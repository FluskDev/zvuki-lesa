# SEO production readiness — дизайн

Дата: 2026-07-20

## Цель

Подготовить существующий SEO-контур к production-сборке: получать маршруты prerender из PostgreSQL, добавить полные metadata и структурированные данные страницам домиков, устранить дублирующую и фиктивную Schema.org-разметку главной страницы, создать корректное Open Graph-изображение и локально проверить итоговый HTML.

## Границы работ

В рамках реализации:

- локальные изменения кода и зависимостей;
- чтение PostgreSQL во время prebuild;
- metadata и JSON-LD для главной и страниц домиков;
- создание `public/og-image.jpg` размером 1200×630 из существующей фотографии;
- автоматические тесты, lint, TypeScript и локальная production-сборка;
- подготовка точного чек-листа действий с контентом и production-раздачей.

Вне рамок реализации:

- применение миграций к общей или production-БД;
- запуск `seed:drafts` на общей или production-БД;
- массовая публикация SEO-страниц и статей;
- изменение production reverse proxy или сервера;
- отправка sitemap в Яндекс Вебмастер или Google Search Console;
- git-коммит без отдельной команды пользователя.

## 1. Prerender-маршруты из PostgreSQL

### Текущее состояние

`scripts/fetch-slugs.mjs` использует `better-sqlite3` и файл `backend/data/zvuki-lesa.db`, хотя backend работает через PostgreSQL. Из-за этого prebuild может молча сформировать только статические маршруты, не включив опубликованные `/seo/*` и `/blog/:slug`.

### Решение

- Заменить SQLite-подключение в `scripts/fetch-slugs.mjs` на пакет `postgres`.
- Добавить `postgres` в корневые `devDependencies`, потому что root build должен быть самодостаточным и не зависеть от разрешения модулей внутри `backend/node_modules`.
- Удалить неиспользуемые `better-sqlite3` и `@types/better-sqlite3` из корневого пакета, если поиск подтвердит отсутствие других потребителей.
- Читать `DATABASE_URL` из окружения. Для локальной сборки загрузить `backend/.env`, если файл существует; внешняя переменная окружения имеет приоритет.
- Выполнить read-only запросы:
  - активные домики → `/booking/:slug`;
  - опубликованные SEO-страницы → `/seo/:slug`;
  - опубликованные статьи → `/blog/:slug`.
- Объединить результаты со статическими маршрутами `/`, `/blog`, `/search`, удалить дубликаты и вывести только JSON в stdout.
- Диагностические сообщения выводить в stderr, чтобы перенаправление stdout в `.prerender-routes.json` всегда создавало валидный JSON.
- Закрывать PostgreSQL-соединение в `finally`.

### Ошибки

- Если `DATABASE_URL` отсутствует, скрипт выводит предупреждение и формирует только статические маршруты. Это сохраняет возможность собрать свежий clone без БД.
- Если `DATABASE_URL` задан, но подключение или запросы завершились ошибкой, скрипт возвращает ненулевой exit code. Деградированная SEO-сборка не должна выпускаться незаметно.

## 1.1. Доступ prerender к backend API

Puppeteer рендерит собранный SPA через временный статический сервер, поэтому относительные `/api/*` и `/uploads/*` без proxy попадут в SPA fallback вместо backend. `scripts/prerender.mjs` должен проксировать эти пути на `PRERENDER_API_URL` (по умолчанию `http://localhost:3001`) и до рендера проверять доступность API. Backend запускается отдельно владельцем окружения; скрипт не стартует и не останавливает общие процессы.

Чтобы read-only prerender не создавал события аналитики, Puppeteer перехватывает `POST /api/analytics/event` и возвращает локальный успешный ответ без отправки запроса backend. Для data-driven маршрутов prerender считается неуспешным, если итоговый HTML остался в loading/not-found состоянии.

`SeoPage` и `BlogPost` не должны вручную удалять `script[data-seo-schema]` после загрузки: жизненным циклом JSON-LD полностью владеет `useDocumentHead`. Существующие эффекты, которые сразу удаляют добавленную Schema, удаляются.

## 2. Metadata и Schema.org страниц домиков

### Metadata

`BookingPage` всегда вызывает `useDocumentHead`, не нарушая Rules of Hooks. До получения данных используются безопасные значения маршрута; после загрузки `Cottage` выставляются:

- уникальный `title` с названием домика и географией;
- `description` из краткого описания и основных характеристик;
- canonical `https://zvuki-lesa.ru/booking/:slug`;
- абсолютный `og:image` из главного изображения домика;
- `og:title`, `og:description`, `og:url`;
- соответствующие Twitter Card metadata.

Для отсутствующего домика устанавливается `robots: noindex, nofollow`.

### JSON-LD

Страница домика получает `@graph`:

1. `LodgingBusiness` комплекса «Звуки Леса» с постоянным `@id`, адресом, координатами и контактами.
2. `Accommodation` конкретного домика с названием, описанием, URL, изображениями, вместимостью, площадью и `amenityFeature`.
3. `Offer` с базовой ценой за ночь и валютой RUB, связанный с `Accommodation`.
4. `BreadcrumbList`: Главная → Домики → текущий домик.

В Schema попадают только существующие значения. Пустые изображения, удобства или некорректные числовые поля не публикуются.

## 3. Единая Schema.org главной страницы

### Проблема

Route-specific JSON-LD находится непосредственно в `index.html`, поэтому SPA-шаблон наследует разметку главной на других маршрутах. Дополнительно `Reviews` добавляет второй неполный `LodgingBusiness`, а статический объект содержит фиктивный рейтинг 5.0 и 50 отзывов.

### Решение

- Удалить route-specific JSON-LD из `index.html`. Базовые meta-теги остаются fallback до выполнения React.
- Выделить домашний React-компонент маршрута внутри существующей структуры `App.tsx`.
- Домашний маршрут один раз вызывает `useReviews`, передаёт результат секции `Reviews` и использует те же данные для Schema. Повторного запроса отзывов не будет.
- Сформировать единый набор JSON-LD:
  - полный `LodgingBusiness`;
  - реальный `AggregateRating` и `Review[]`, только если API вернул отзывы;
  - `BreadcrumbList`;
  - существующий `FAQPage`;
  - `ImageObject` для Open Graph-изображения.
- При ошибке API отзывов публикуется полноценный `LodgingBusiness` без `aggregateRating` и `review`. Фиктивные значения не используются.
- Домашний маршрут также явно восстанавливает свои title, description, canonical и social metadata после SPA-навигации.

## 4. Расширение `useDocumentHead`

`DocumentHead` расширяется поддержкой:

- `robots`;
- `ogTitle`, `ogDescription`, `ogUrl`;
- Twitter title, description, URL и image.

Если отдельные social-поля не переданы, используются `title`, `description`, `canonical` и `ogImage`. Это сохраняет простой API для существующих страниц и делает prerendered `<head>` согласованным.

Хук продолжает удалять только управляемые им JSON-LD-скрипты. При смене маршрута новая страница обязана явно установить собственные основные metadata; главная и страницы домиков будут это делать.

## 5. Open Graph-изображение

Из `public/cabin-1-enhanced.jpg` создаётся `public/og-image.jpg`:

- размер 1200×630;
- обрезка по центру с сохранением пропорций;
- JPEG с качеством, достаточным для социальных превью;
- без добавления текста или логотипа, чтобы не вводить новый визуальный дизайн без отдельного согласования.

Все существующие абсолютные ссылки `https://zvuki-lesa.ru/og-image.jpg` после этого перестают вести на отсутствующий файл.

## 6. Локальная проверка

### Автоматические проверки

- Дополнить тесты `useDocumentHead`: Open Graph, Twitter, robots, canonical и очистка управляемой Schema.
- Добавить тест главной Schema с отзывами и без отзывов; подтвердить отсутствие фиктивного рейтинга и наличие ровно одного `LodgingBusiness`.
- Добавить тест `BookingPage` с mocked API: уникальные metadata, canonical, `Accommodation`, `Offer` и `BreadcrumbList`.
- Проверить сценарий 404 домика с `noindex, nofollow`.
- Выполнить frontend tests, backend sitemap test, lint и TypeScript/build.

### Проверка build-результата

После read-only запуска prebuild с настроенной PostgreSQL проверить:

- `.prerender-routes.json` является валидным JSON;
- опубликованные записи присутствуют как `/seo/*` и `/blog/:slug`;
- активные домики присутствуют как `/booking/:slug`;
- соответствующие `dist/**/index.html` созданы;
- в каждом HTML правильные title, description, canonical, Open Graph и route-specific JSON-LD;
- Schema главной отсутствует в HTML статей, SEO-страниц и домиков.

## 7. Production-чек-лист без выполнения действий

После локальной реализации владелец окружения должен:

1. Сделать резервную копию БД.
2. Применить актуальные миграции.
3. Выполнить `seed:drafts`, если черновики ещё не загружены.
4. Проверить и вручную опубликовать нужные SEO-страницы и статьи в админке.
5. Запустить production build с корректным `DATABASE_URL`.
6. Проверить, что published-маршруты попали в `.prerender-routes.json` и `dist/`.
7. Настроить reverse proxy так, чтобы `/sitemap.xml` обслуживался backend-маршрутом, а prerendered HTML — статическим сервером с SPA fallback только для отсутствующих файлов.
8. Проверить итоговый HTML внешним HTTP-запросом, а не только DOM браузера.
9. Валидировать JSON-LD и отправить sitemap в Яндекс Вебмастер и Google Search Console.

## Критерии готовности

- Root build больше не читает SQLite.
- Настроенное PostgreSQL-подключение не может молча деградировать до статического списка при ошибке.
- Все записи, которые опубликованы или активны в подключённой БД, попадают в prerender manifest.
- Каждая страница домика имеет уникальные metadata и семантически связанный `LodgingBusiness` + `Accommodation` JSON-LD.
- Главная содержит один полный `LodgingBusiness`; фиктивный рейтинг отсутствует.
- Route-specific Schema главной не появляется на других маршрутах.
- `/og-image.jpg` существует и имеет размер 1200×630.
- Автоматические проверки и локальная production-сборка проходят.
- Общая/production-БД и production-сервер не изменены.
